# Building V8 15.x for GodotJS

This file is the reference for the 15.x-specific parts of the build. It explains
why each extra setting exists, what it costs, and what has not been verified.

The short version: a 15.x build needs four extra gn args, a patched assembler
flag, and a newer libstdc++ on Linux. The embedder (GodotJS) has to compile as
C++20 and link `libatomic`. Nothing else about the package layout changes.

---

## 1. The four extra gn args

V8 15 turns four things on by default that either do not compile with libstdc++
or drag in a toolchain we do not want to download. gn rejects an argument a
given V8 version does not declare, so these cannot go into the per-platform
`v8.<platform>_<arch>.args.gn` files (that would break the 12.x and 13.x
builds). They live in `v8.extra_15.x.args.gn`, and `prepare_v8_build.sh`
appends that file only when the version is 15 or newer.

| Arg | What happens if you leave it on | Cost of turning it off |
|---|---|---|
| `v8_enable_partition_alloc = false` | Does not compile with libstdc++: `partition_alloc/internal_allocator_forward.h: error: unknown type name 'size_t'` (partition_alloc is written against libc++) | None for an embedder. V8's own comment in `BUILD.gn` says it "has no effect on V8 when it is embedded elsewhere"; `V8_ENABLE_PARTITION_ALLOC` only appears in `src/d8/*` and in one sandbox-only call site, and the sandbox is off too |
| `v8_enable_temporal_support = false` | Pulls the Rust toolchain (`third_party/rust-toolchain`, ~276 MB) | None. `Temporal` needs `--harmony-temporal` at runtime anyway, so `Temporal` is `undefined` in normal JS either way |
| `enable_rust = false` | `build/config/rust.gni` fails reading `third_party/rust-toolchain/VERSION` | None. In V8 15 only Temporal uses Rust |
| `v8_enable_fuzztest = false` | `test/unittests/BUILD.gn` pulls `third_party/fuzztest`, which pulls protobuf | None. Only V8's own fuzz targets use it; `v8_monolith` does not |

`v8_enable_sandbox = false` is **not** one of these. It is already in every
platform args file. In 15.x it is a tri-state string that gn derives on its
own; assigning `false` to it is still accepted.

### ICU is on

`v8_enable_i18n_support = true` in every platform args file, so `Intl.*` and
RegExp `\p{Script=...}` property escapes work, and each platform directory in
the bundle carries `icudtl.dat` (ICU is built with `icu_use_data_file = true`,
so the language data is a separate file, not inside the monolith). Two
consequences:

- `third_party/icu` must not be trimmed from the checkout (see section 5).
- Turning Temporal back on later would gain its timezone support from this ICU.

## 2. ELF CREL: off by default

Since V8 15, `//build/config/compiler/BUILD.gn` adds
`-Wa,--crel,--allow-experimental-crel` when building for Linux with lld. CREL is
a compact relocation encoding that **only lld can read**. A `libv8_monolith.a`
built that way cannot be linked with GNU binutils; `g++` reports

```
error in libv8_monolith.a(maglev-graph-builder.o)(.eh_frame);
no .eh_frame_hdr table will be created
```

which gives no hint that lld is involved. In binutils 2.46 `as` does not even
have a `--crel` option, and `nm` / `objdump` / `ar` / `objcopy` cannot read a
CREL archive (use `llvm-nm` / `llvm-objdump`).

`prepare_v8_build.sh` therefore disables it by rewriting the condition to
`if (false && ...)`. It does not match a whole line, because `gn format` splits
that condition over two lines: the script finds the cflags line containing
`--crel`, walks up to the nearest `if (` line, and guards it.

```sh
bash prepare_v8_build.sh <v8_source_dir> <args_gn_path> <v8_version>
```

- version major < 15 → prints `needs no adjustments`, exit 0
- version not parseable → exit 2
- >= 15 → appends `v8.extra_15.x.args.gn`, then disables CREL unless `V8_KEEP_CREL=1`
- running it twice is safe: prints `ELF CREL already disabled`, exit 0

### Turning CREL back on

Both repositories have to change together; changing one side fails the build.

1. Here: pass `V8_KEEP_CREL=1` to `prepare_v8_build.sh` (the script supports it,
   no workflow sets it yet — add `V8_KEEP_CREL: "1"` to the job's `env:`, or
   thread an input through `build_all.yml`).
2. GodotJS: install `lld` and link the engine with `-fuse-ld=lld`. GodotJS has
   no `-fuse-ld` anywhere today, so enabling CREL now would break its packaging
   workflow.

Benefit, with a caveat: measured archive size 90,956,752 B with CREL vs
106,921,784 B without, but those two builds also differed in synced dependencies
(1323 vs 1354 gn targets), so the 16 MB is not cleanly attributable to CREL. A
clean A/B needs one build with only this variable changed (~35 min). CREL also
speeds up **V8's own** link step, not Godot's.

Check whether CREL is in an archive:

```sh
mkdir -p /tmp/chk && cd /tmp/chk && ar x <path>/libv8_monolith.a
readelf -S $(ls *.o | head -50) | grep -c crel   # 0 = disabled
grep -c crel out.gn/x64.release/build.ninja      # 0 = disabled
```

## 3. Linux needs a newer libstdc++

V8 15 uses `std::atomic_ref` (`src/base/atomicops.h`, `src/base/memcopy.h`) and
`std::hardware_destructive_interference_size` (`src/heap/mutable-page.cc`, in a
`static_assert`). libstdc++ only provides those from GCC 12, while
`ubuntu-22.04` ships GCC 11. The two Linux jobs install `g++-13` when the
version is 15 or newer; clang automatically uses the newest GCC installation it
finds, so no `cc`/`cxx` args are needed. `std::format` (GCC 13) is not compiled
in the current configuration, so GCC 12 would probably do; 13 is margin.

`v8.linux_*.args.gn` also sets `use_sysroot = false`. Without it V8 cross-builds
against the Debian bullseye sysroot inside the checkout, whose libstdc++ is GCC
10 and lacks those two features — the failure looks like missing headers
(`std::bit_cast`, `<source_location>`), not like a toolchain problem. The cost
is explicit: **the glibc floor of the Linux artifacts becomes the runner's
glibc (2.35, Ubuntu 22.04+)**, because Godot does not use a sysroot either.

Android is unaffected (NDK clang + NDK libc++); macOS/iOS use Apple libc++.

## 4. Embedder side (GodotJS)

These are the changes GodotJS must make to consume a 15.x package. They are
listed here because two of them decide whether a switch here can be turned on.

1. **C++20, hard requirement.** `include/v8config.h` has
   `#if __cplusplus <= 201703L / #error "C++20 or later required."`. Godot
   prepends `-std=gnu++17` (MSVC: `/std:c++17`) precisely so a module can
   override it, so the module appends `-std=gnu++20` to its own environment.
   MSVC needs the engine's `/std:c++17` removed first (two `/std:` flags fight)
   and Godot already passes `/Zc:__cplusplus`, so `__cplusplus` is accurate.
2. **`-latomic` on Linux/Android.** A 15.x monolith has 13 undefined
   `__atomic_compare_exchange` references (a 12.x one has none): V8 does 128-bit
   compare-exchanges on objects that are only 8-byte aligned, so the compiler
   emits the generic libcall instead of `cmpxchg16b`, and `-mcx16` does not
   remove it. libatomic is not distributed with V8. This is unrelated to lld.
   Apple toolchains do not ship libatomic; `llvm-nm -u` finds no `__atomic_*`
   reference in the macOS/iOS archives, so those platforms are left alone.
3. **`V8_COMPRESS_POINTERS`** must be defined when compiling the embedder, or V8
   fatals with an embedder-vs-V8 configuration mismatch. GodotJS already does
   this for non-iOS/Android.
4. **Version pin**: `deps_v8_version` and `deps_release_tag` in GodotJS's
   `SCsub` must match a published release asset name exactly
   (`v8_<version>.zip`), or the download 404s.

## 5. Local build recipe (Linux x86_64)

```sh
python3 ./tools/dev/v8gen.py x64.release
cp <this repo>/v8.linux_x86_64.args.gn out.gn/x64.release/args.gn
bash <this repo>/prepare_v8_build.sh . out.gn/x64.release/args.gn 15.7.112.12
ninja -C out.gn/x64.release v8_monolith -j 16
```

Output: `out.gn/x64.release/obj/libv8_monolith.a`. About 35 minutes on 16
cores, ~1354 gn targets (684 targets / 2083 build steps when the test data and
Rust dependencies are trimmed).

The archive is a fat archive (`!<arch>`, no `-T -S`), so it can be distributed
as is. The intermediate `obj/*.a` (e.g. `libv8_libbase.a`) are *thin* archives
from `//build/config/compiler:thin_archive` — lld reads them, `ld.bfd` cannot,
which is why `use_lld = false` fails earlier, when linking the host tools.

Link test:

```sh
g++ -std=c++20 -O1 -DV8_COMPRESS_POINTERS main.cc \
    -I v8/include -L v8/linux.x86_64.release \
    -lv8_monolith -latomic -lpthread -ldl -lrt
```

Expect the program to print `V8 version: <the version you built>`.

If `Intl` is on, the probe must also point V8 at the ICU data. `v8::V8::InitializeICU`
takes the **path to `icudtl.dat`**, not the directory containing it — that is why
`InitializeICUDefaultLocation` appends `icudtl.dat` to the executable's directory
itself (`src/init/icu_util.cc`). Passing a directory makes the mmap fail and every
`Intl` call later reports `TypeError: Internal error. Icu error.`, with
`Date.prototype.toLocaleDateString` aborting the process.

### When `gclient sync` is not an option

On a machine where depot_tools' `gsutil.py` never returns (it hangs at zero bytes
on `gs://` copies while plain HTTPS to the same bucket is fine), fetch the few
non-git dependencies by hand and skip gclient entirely. Everything else in DEPS is
a git dependency and clones normally.

```sh
# gn: the cipd HTTP endpoint works with curl. The revision is DEPS' gn_version.
curl -fL -o gn.zip "https://chrome-infra-packages.appspot.com/dl/gn/gn/linux-amd64/+/${GN_REVISION}"
unzip gn.zip && install -m755 gn buildtools/linux64/gn

# clang / libclang: the object names and sha256 are listed in DEPS itself
curl -f -o clang.tar.xz \
  https://storage.googleapis.com/chromium-browser-clang/Linux_x64/clang-<CR_REVISION>.tar.xz
tar -xJf clang.tar.xz -C third_party/llvm-build/Release+Asserts
curl -f -o libclang.tar.xz \
  https://storage.googleapis.com/chromium-browser-clang/Linux_x64/rust-libclang-<...>.tar.xz
tar -xJf libclang.tar.xz -C third_party/llvm-libclang
```

Three more things gclient normally does for you:

- `build/config/gclient_args.gni` is generated by gclient (DEPS' `gclient_gn_args_file`).
  Without it `gn gen` dies with `Unable to load "//build/config/gclient_args.gni"`.
  Writing the two `gclient_gn_args` values by hand is enough.
- Do not leave `depot_tools` on `PATH` when running ninja: its `python3` shim needs a
  cipd bootstrap and fails with `python3_bin_reldir.txt not found`. gn is invoked as
  `//buildtools/linux64/gn`, so nothing else needs depot_tools.
- `third_party/cpython3/host/bin/python3` missing makes `exec_script` return
  127; symlink the system python.

A distro `gn` is too old and fails with `ERROR at //.gn:12:5: Undefined identifier`;
use the pinned one (2595 for 15.7.112.12).
- `apt install libglib2.0-dev`, or `gn gen` fails with
  `Package glib-2.0 was not found in the pkg-config search path`.
- When trimming dependencies with `custom_deps`, the key must include the
  solution name prefix (`v8/test/test262/data`, not `test/test262/data`).
  These cannot be trimmed: `third_party/icu` (needed now that i18n is on),
  `tools/clang`, `third_party/jinja2`, `third_party/markupsafe`,
  `third_party/googletest/src`, `third_party/fuzztest`,
  `third_party/llvm-libc/src`.

## 6. Verified / not verified

Verified locally on Linux x86_64 with **15.7.112.12 and `v8_enable_i18n_support = true`**
(the current default of this branch), built without depot_tools' gsutil path:

- `ninja v8_monolith`: 2083/2083 steps, 0 errors. `libv8_monolith.a` =
  122,879,868 B, fat archive (`!<arch>`, 1725 members), no `.crel.*` sections.
- `nm -u` shows 17 undefined `__atomic_compare_exchange`; dropping `-latomic` from
  the link reproduces `undefined reference to '__atomic_compare_exchange'`, so the
  requirement in section 4 is real, not theoretical.
- Linked with the system `g++` (GNU `ld.bfd`) and run: `V8 version: 15.7.112.12`,
  `Intl.NumberFormat` → `1,234,567.891`, `Date.toLocaleDateString('zh-CN')` →
  `2026/1/2`, `/\p{Script=Han}/u` → `true`.

Also verified locally on 15.6.75.19 earlier (i18n off at the time), and 15.7.112.12
through CI release `1.2.0`:
- Every platform library in the published bundle was checked with
  `llvm-objdump -f` for its actual object format (mach-o / elf / coff, including
  a real coff-arm64 for Windows arm64).
- `prepare_v8_build.sh` was exercised against fixtures: default patch, idempotent
  re-run, `V8_KEEP_CREL=1` keeps CREL, `13.5.119` is skipped, a bad version
  exits 2. Re-confirmed on this build: it appends the four 15.x args and rewrites
  the CREL condition to `if (false && is_linux && use_lld && ...)`.

Not verified:

- macOS / iOS / Android jobs. The change to those workflows is one added script
  call, but it has not run on a real runner. Whether Apple platforms need
  `libatomic` at link time is unconfirmed.
- The Windows cmd inline arg appendage (cannot be run locally).
- `g++-13` availability on the `ubuntu-22.04` runner image.
- Exact CREL size/time difference (see section 2).
- iOS simulator libraries are not built at all (`build_all.yml` only wires
  `v8_ios_arm64`), while GodotJS's `SCsub` lists `ios.x86_64` and `ios.arm32`.
