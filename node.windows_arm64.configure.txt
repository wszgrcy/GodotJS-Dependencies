# ./configure arguments for Node.js on Windows arm64.
# See node.linux_x86_64.configure.txt for what the shared options do.
#
# Run configure from the "VS 2022 ARM64 Native Tools Command Prompt" (on an x64
# machine that is vcvarsall's amd64_arm64 pair). No CI job builds this file today:
# the matrix note in .github/workflows/build_node.yml explains why cross-building
# arm64 Windows from an x64 runner is left out, and this file is the recipe for the
# native arm64 runner that entry waits for.

--ninja
--dest-cpu=arm64
# Node calls Windows "win"; naming the target keeps the file honest
# about what it cross-compiles to when a runner differs.
--dest-os=win

--with-intl=full-icu
--without-node-options
--without-npm
--disable-single-executable-application

# Node 24 and newer are built on Windows with clang-cl instead of cl.exe
# (BUILDING.md calls it a requirement), and the option carries the LLVM version:
# ./configure --clang-cl=19.1.5. A bare --clang-cl stops configure with
# "argument --clang-cl: expected one argument".
#
# The version is a property of the machine, not of this file, so the option is not
# written here: the CI job reads `clang-cl --version` - the same thing Node's own
# vcbuild.bat does - and appends --clang-cl=<version> to the arguments. Building by
# hand on Windows means adding that option yourself, with the version you have.
#
# --clang-cl only records which toolchain the build is meant for; it does not change
# the compiler ninja runs. Two more things are needed to really compile with clang-cl,
# and they are described in node.windows_x86_64.configure.txt: handing gyp the compiler
# path through GODOTJS_NODE_CLANG_CL (patches/godotjs-gyp-win-clang-cl.patch reads it
# inside gyp) and exporting CXXFLAGS=/std:c++20, because Node asks for the standard
# through msvs_settings' LanguageStandard and gyp marks that as MSBuild-only, so ninja
# drops it and the compiler falls back to its own default.
#
# None of that is enough for arm64 from an x64 machine, and this file is only a recipe
# for a native arm64 Windows machine, because three separate gaps all have to close:
#   - gyp gives the host toolset the same architecture as the target, so the build-time
#     tools (mksnapshot, torque) would be built as arm64 and could not run on the runner.
#     Generating the ninja files with the Windows flavour shows it directly:
#     obj.host/... says `arch = environment.arm64`.
#   - clang-cl on an x64 host needs --target=aarch64-windows-msvc as well, and gyp's
#     clang-cl hook only appends -m32/-m64.
#   - Temporal's Rust archive collides between the two toolsets (the guard in
#     prepare_node_build.sh explains it and the two ways out).
# A native arm64 machine has no toolset split and clang-cl already targets its own
# architecture, so only the Temporal note stays relevant there.
